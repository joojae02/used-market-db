# 문서 간 불일치 정리

3조 산출물끼리 서로 다르게 적힌 부분과, 문서와 코드가 다른 부분을 모았다.
기준일은 2026-11-19이고, 드라이브 최종본을 기준으로 했다.

- **1~5장**: 문서끼리 어긋난 것이다. 팀이 하나로 정해야 한다.
- **6장**: 문서는 맞는데 코드가 덜 된 것이다.
- **7장**: 문서가 정해지기 전까지 코드가 임시로 따르는 해석이다.
- **8장**: 11/19 피드백과 전체 점검에서 고친 논리 오류다.

## 1. 전체에 걸친 문제

### 1-1. 단위업무 번호가 두 갈래 🔴

같은 업무를 문서마다 다른 번호로 부른다.

| 업무 | 기능도 · DDL | 기술서 제목 · 흐름도 |
| --- | --- | --- |
| 거래 상태 변경 | **PRD-04** | PRD-03 |
| 예약자 지정 | **TRD-04** | TRD-03 |
| 거래 완료 처리 | **TRD-05** | TRD-04 |
| 신고 | **TRS-03** | TRS-01 |
| ADM-03 이름 | 신고 **처리** | 신고 **관리** |

- 기술서 PRD-03 본문은 TRD-04·TRD-05(기능도 번호)를 쓴다. 그래서 기술서 안에서도 번호가 충돌한다.
- 기능도에는 PRD-03, TRD-03, TRS-01·02가 비어 있다.

**제안**: 기능도 번호를 기준으로 하고, 기술서 제목과 흐름도를 고친다. 이게 수정량이 가장 적다.
**지금 코드**: 주석과 README는 기능도 번호를 쓴다.

### 1-2. 알림/안내 기능이 데이터 모델에 없음 🔴

기술서는 여러 업무에서 "~에게 안내한다/알린다"고 적었다. 하지만 개념·논리·물리ERD와 DDL에는 알림을 저장할 테이블이 없다.

| 기술서 | 누구에게 | 무엇을 |
| --- | --- | --- |
| TRD-01 ⑨ | 판매자 | 새 채팅방 개설 |
| TRD-02 ⑤ | 상대방 | 새 메시지 도착 |
| TRD-03 ⑩ | 구매자 | 예약 지정·해제 결과 |
| TRD-04 ⑮ | 최종 구매자 | 거래 완료 |
| ADM-01 ⑬ | 제재 대상 회원 | 제재 유형·사유·기간 |
| ADM-02 ⑫ | 판매자 | 게시글 조치 유형·사유 |
| ADM-03 ⑬ | 신고자 | 처리 완료 여부 |

**제안**: 둘 중 하나로 정한다.
- **범위에서 제외**: 기술서 문구를 "화면에서 확인할 수 있다"로 바꾼다. 수정량이 적다.
- **알림 테이블 추가**: 알림번호, 수신회원번호, 유형, 내용, 생성일시, 읽은일시를 갖는 테이블을 ERD 3종과 DDL에 추가한다.

**지금 코드**: 알림이 없다. 대신 채팅 목록의 안 읽은 개수와 내 정보 화면의 신고 처리 상태로 일부를 확인할 수 있다.

### 1-3. 용어·값 통일 🟡

| 항목 | 기능도 | 기술서 | 개념ERD | 논리·물리ERD | DDL |
| --- | --- | --- | --- | --- | --- |
| 거래 완료 상태값 | **거래완료** | 판매완료 | — | 판매완료 | 판매완료 |
| 거래 상태를 부르는 말 | **상품 상태** | 거래 상태 | 거래상태 | 거래상태 | trade_status |
| 물건의 상태 | — | **상품 상태** | 물품상태 | 물품상태 | item_condition |
| 물품상태 값 | — | 정의 없음 | — | 정의 없음 | 새상품 / 거의새것 / 사용감있음 / 하자있음 |
| 상품 엔티티 | 상품 | 상품 / 상품 게시글 | 상품 게시글 | PRODUCT | product |
| 게시글 조치 엔티티 | — | 게시글 관리 이력 | 게시글 조치 | PRODUCT_ACTION | product_action |
| 신고 처리 엔티티 | 신고 처리 | 신고 처리 | 신고 처리 | REPORT_PROCESS | 신고 처리 **이력** |
| 권한 값 | — | — | 권한 | **0~3 숫자 코드** | user / moderator / staff / root 문자열 |
| 조치유형 | — | 블라인드 해제 | — | 블라인드 해제 | 블라인드해제 (붙여씀) |
| 신고 처리 결과 | — | 조치 완료 (띄어씀) | — | 조치완료 | 조치완료 |
| 플랫폼 이름 | 중고거래 플랫폼 | 1쪽만 중고거래 플랫폼 **"이름"** | — | — | used_market |

**제안**
- 상태값은 **판매완료**로 통일한다. 기능도 두 곳만 고치면 된다.
- 거래 상태는 **거래상태**, 물건 상태는 **물품상태**라고 부른다. "상품 상태"는 둘 중 무엇인지 헷갈린다.
- 권한은 ERD 표기를 DDL처럼 문자열로 바꾼다.
- 플랫폼 이름을 정해 모든 문서에 넣는다.

## 2. 회원 (MEM)

### 2-1. 별도 `관리자` 엔티티 🔴

| 문서 | 내용 |
| --- | --- |
| 기술서 엔티티 내역 #6 | 별도 `관리자` 엔티티 (관리자번호, 관리자아이디, 패스워드해시, 관리자권한, 계정상태) |
| 회의록 11/10, ERD 3종, DDL | 관리자 테이블이 없다. `회원.role`로 구분하고, 관리자번호 = 회원번호 |

**제안**: 엔티티 내역에서 `관리자`를 지우고, `회원`에 `권한`을 추가한다. ADM 업무의 "관리자번호"는 "관리자 회원번호"로 바꾼다.

### 2-2. "아이디"라는 속성 🔴

| 문서 | 내용 |
| --- | --- |
| 기술서 MEM-02 ①② | **닉네임** + 패스워드로 로그인 |
| 기능도 MEM-01 | "**아이디**/닉네임 중복 확인" |
| 기술서 ADM-01 ② | 회원번호, **아이디**, 닉네임으로 검색 |
| ERD 3종, DDL | 아이디 컬럼이 없다 (닉네임·이메일·전화번호가 UNIQUE) |

**제안**: "아이디 = 닉네임"으로 정하고, 기능도와 ADM-01 ②의 "아이디"를 지운다.
**지금 코드**: 닉네임으로 로그인한다.

### 2-3. 탈퇴 시 개인정보 삭제 vs 같은 계정 재사용 🔴

| 문서 | 내용 |
| --- | --- |
| 기술서 MEM-01 ⑧⑨ | 탈퇴하면 개인정보를 삭제하거나 분리 보관한다. 재가입은 최초 가입과 같은 절차 |
| 회의록 11/10, DDL (P-01, P-02) | 같은 row를 '정상'으로 되돌려 재사용한다. 게시글과 판매 기록은 보존한다 |

두 규칙은 같이 지킬 수 없다.
- 개인정보를 지우면 재가입한 사람을 원래 row에 연결할 방법이 없다.
- 지우지 않으면 닉네임·이메일·전화번호 UNIQUE 때문에 같은 값으로 신규 가입을 할 수 없다.

**제안**: "재가입 = 이메일로 기존 계정을 찾아 다시 활성화"로 정하고, 기술서 ⑧⑨를 고친다.
**지금 코드**: 이 방식이고, 탈퇴해도 개인정보는 지우지 않는다.

### 2-4. 탈퇴 제한 조건 🟡

| 문서 | 내용 |
| --- | --- |
| 기술서 MEM-01 ⑦ | **판매중** 상품이 있으면 거래를 완료하거나 삭제해야 한다 |
| 흐름도 2쪽 | "진행 중인 거래/상품 확인" |
| DDL | 강제 장치 없음 (앱에서 처리) |

**예약중** 상품도 막는지 정해져 있지 않다.
**제안**: "판매중·예약중 상품이 있으면 탈퇴할 수 없다"로 적는다.
**지금 코드**: 판매중과 예약중을 모두 막는다.

### 2-5. 로그인 실패 사유 "피신고 계정" 🟡

| 문서 | 내용 |
| --- | --- |
| 흐름도 2쪽 | 로그인 실패 화살표 라벨: "불일치/**피신고 계정**" |
| 기술서 MEM-02 ④ | 계정상태가 '정상'이 아니면(이용정지·탈퇴) 로그인 불가. 신고를 받았다는 이유만으로는 막지 않는다 |

**제안**: 흐름도 라벨을 "불일치/이용정지·탈퇴 계정"으로 고친다.

### 2-6. 권한(role) 관리 업무가 없음 🔴

| 문서 | 내용 |
| --- | --- |
| 회의록 11/10 | 4단계 권한. 루트는 하나만 존재하고, 삭제·권한 변경이 불가능하며, 다른 회원의 권한을 관리한다 |
| ERD 3종, DDL | role 컬럼, 루트 보호 트리거 (P-05~P-08) |
| 기능도, 기술서, 흐름도 | "관리자"만 나온다. 권한 부여·회수 업무가 없다 |
| DDL 주석 | moderator와 staff의 기능 구분은 팀에서 아직 정하지 않았다 |

**제안**: 기능도에 권한 관리 업무(예: ADM-04)를 추가하고, moderator와 staff가 각각 무엇을 할 수 있는지 정한다.
**지금 코드**: 권한 변경은 루트만 할 수 있다. moderator, staff, root는 나머지 관리 기능에서 똑같이 동작한다.

## 3. 상품·거래·채팅 (PRD, TRD)

### 3-1. 거래 완료 경로, 예약자 ≠ 구매자일 때 🔴

| 문서 | 내용 |
| --- | --- |
| 흐름도 1쪽 | 판매완료는 예약중을 거쳐서만 간다 |
| 기술서 TRD-04 ④ | 예약중이면 예약자를 구매자로 고를 수 있다. 예약자와 실제 구매자가 다르면 **예약을 해제한 뒤** 다시 지정한다 |
| DDL | 판매중에서 바로 판매완료로 갈 수 있고, 구매자 ≠ 예약자도 허용한다 |

정해야 할 것은 두 가지다.
1. 판매중에서 바로 거래를 완료할 수 있는가?
2. 예약중일 때 예약자가 아닌 사람과 바로 완료할 수 있는가? 기술서는 "안 된다(해제 먼저)"로 읽힌다.

**제안**: 1은 허용하고(흐름도에 경로 추가), 2는 기술서대로 "예약 해제 후 지정"으로 한다.
**결정 (11/19 피드백)**: 2는 "예약자 아닌 사람과 완료 불가"로 확정했다. API가 409로 막고, DDL 트리거 `trg_product_trade_rule`도 같은 규칙을 강제한다. 1은 아직 허용 중이니 흐름도에 경로를 추가해야 한다.

### 3-2. 구매자 수령 확인 단계 🔴

| 문서 | 내용 |
| --- | --- |
| 흐름도 1쪽 | 판매자 "물품 전달" → 구매자 "물품 수령 확인" → 판매자 거래 완료 |
| 기술서 TRD-04, 기능도 TRD-05 | 판매자가 혼자 완료 처리한다. 구매자 확인 단계는 없다 |
| DDL | 수령 확인 컬럼이 없다 |

**제안**: 흐름도의 수령 확인을 "오프라인 단계(시스템 기록 없음)"로 표시하거나 지운다.

### 3-3. 채팅방 중복 개설 기준 🟡

| 문서 | 내용 |
| --- | --- |
| 기술서 TRD-01 ④ | 이미 **활성화된** 방이 있으면 기존 방으로 연결한다 (비활성 방이면 새로 만들 수 있다는 뜻으로 읽힌다) |
| 기능도 TRD-01 | 중복 개설 방지 |
| DDL | `UNIQUE (product_no, buyer_no)`: 상태와 상관없이 상품·구매자당 방 하나 |

**제안**: 기술서 문구를 "이미 채팅방이 있으면"으로 바꾼다.

### 3-4. 거래 완료 후 채팅방 1개월 유지 🟡

| 문서 | 내용 |
| --- | --- |
| 기술서 TRD-04 ⑩ | 최종 구매자와의 방은 완료 후 1개월간 활성 상태를 유지한다 |
| DDL, 흐름도 | 1개월 뒤 처리 규칙이 없다 (`product.completed_at`으로 계산할 수는 있다) |

**제안**: "완료일시부터 1개월이 지나면 메시지를 보낼 수 없다(조회 시 계산)"라고 적는다.
**지금 코드**: 이 방식이다.

### 3-5. 메시지 `읽음여부` 컬럼 🔴

| 문서 | 내용 |
| --- | --- |
| 기술서 TRD-02 ⑥ | 읽음 여부 + 읽은 일시 |
| 개념ERD | `읽음여부`, `읽은일시` |
| 논리·물리ERD | `read_yn` + `read_at` |
| DDL | `read_yn`을 지우고 `read_at IS NULL`로 판단한다 (주석에 명시) |

**제안**: DDL의 결정이 맞다. 읽음여부는 읽은일시만 있으면 알 수 있다. ERD 3종에서 `읽음여부`/`read_yn`을 지운다.

### 4-4. 신고 1건당 처리 이력 개수 🔴

| 문서 | 내용 |

- **1:N으로 갈 때** (재처리 이력 보존): ERD를 고친다.

**지금 코드**: 처리완료·반려된 신고는 다시 처리할 수 없다. 실제로는 1:0..1로 동작한다.
