> 공유된 artifact 링크(`중고거래 플랫폼 DB · 구조와 데이터`)는 다른 사람이 만든 것이라 이 세션에서 읽기 권한 승인을 받지 못해 비교에서 빠졌다. 업무 기능도 / 업무 문서 리스트도 받지 못했다.

우선순위: 🔴 구조가 다름(테이블/컬럼/규칙이 갈림) · 🟡 값·명칭이 다름 · ⚪ 오타·표기

## 1. 🔴 구조·규칙이 갈리는 부분

### 1-1. 관리자 엔티티 존재 여부
- **기술서 엔티티 내역 #6**: 별도 `관리자` 엔티티 (관리자번호, 관리자아이디, 패스워드해시, 관리자권한, 계정상태)
- **회의록2 / ERD / DDL**: 관리자 테이블 없음. `회원.role` (user / moderator / staff / root) 로 관리, 관리자번호 = 회원번호
- 👉 기술서 엔티티 내역에서 `관리자` 삭제, `회원`에 `권한(role)` 추가 필요. ADM-01 ⑦, ADM-02 ⑩, ADM-03 ⑪의 "관리자번호"는 "관리자 회원번호"로 표현 통일 권장.

### 1-2. 기술서 엔티티 내역에 빠진 엔티티·속성
기술서 본문에는 있는데 엔티티 내역(12쪽)에는 없는 것들. ERD·DDL에는 이미 있음.

| 엔티티 | 빠진 것 | 근거 (기술서 본문) |
| --- | --- | --- |
| 채팅 메시지 | **엔티티 자체가 없음** | TRD-02 전체 |
| 회원 | 권한, 연속로그인실패횟수, 로그인제한만료일시 | 회의록2-3, MEM-02 ⑦ |
| 상품 | 구매자회원번호(FK), 거래완료일시 | TRD-04 ⑥ |

### 1-3. 로그인 수단 / "아이디"
- **MEM-02 ①②**: 닉네임 + 패스워드로 로그인
- **ADM-01 ②**: "회원번호, **아이디**, 닉네임…"으로 검색 → 회원에 아이디 속성 없음
- **기술서 엔티티 #6**: 관리자아이디
- **ERD / DDL**: 아이디 컬럼 없음 (닉네임·이메일 UNIQUE)
- 👉 "아이디 = 닉네임"으로 확정하고 ADM-01 ② 문구 수정, 또는 아이디 컬럼 추가 중 결정 필요. (데모 구현은 닉네임 로그인 기준)

### 1-4. 거래 완료 흐름 — 구매자 수령 확인 단계
- **흐름도 1쪽**: 판매자 "물품 전달" → 구매자 "물품 수령 확인" → "수령 완료" → 판매자 TRD-04 거래 완료
- **기술서 TRD-04**: 판매자가 단독으로 판단해 완료 처리. 구매자 확인 단계 없음
- **DDL**: 수령 확인 관련 컬럼 없음
- 👉 흐름도의 수령 확인 단계를 "오프라인 단계(시스템 기록 없음)"로 표시하거나 삭제.

### 1-5. 거래 완료가 '예약중'을 거쳐야 하는가
- **흐름도 1쪽**: 판매완료는 예약중 → 최종 확정 경로로만 그려짐
- **기술서 TRD-04 ④**: 예약중이면 예약자를 구매자로 고를 수 있다고만 되어 있고, 판매중에서 바로 완료 가능한지 불명확
- **DDL**: 판매중 → 판매완료 직행 허용 (구매자 ≠ 예약자도 허용)
- 👉 규칙 하나로 확정 필요. (데모 구현: 판매중/예약중 모두에서 완료 가능, 구매자는 해당 상품 채팅방 참여자로 제한)

### 1-6. 채팅방 중복 개설 규칙
- **기술서 TRD-01 ④**: "이미 **활성화된** 채팅방이 있으면 기존 방으로 연결" → 비활성 방이면 새로 만들 수 있다는 뜻으로 읽힘
- **DDL**: `UNIQUE (product_no, buyer_no)` → 상태와 무관하게 상품·구매자당 1개
- 👉 기술서 문구를 "이미 채팅방이 존재하는 경우"로 바꾸는 쪽이 간단.

### 1-7. 거래 완료 후 채팅방 1개월 유지
- **기술서 TRD-04 ⑩**: 최종 구매자 방은 완료 후 1개월 활성 유지 (이후 비활성 전환 암시)
- **DDL / 흐름도**: 1개월 후 전환 규칙·배치 없음 (product.completed_at으로 계산은 가능)
- 👉 "완료일시 + 1개월 지나면 전송 불가"를 조회 시 계산으로 처리한다고 명시 권장.

### 1-8. 메시지 읽음 여부 속성
- **기술서 TRD-02 ⑥**: 읽음 여부 + 읽은 일시
- **ERD**: `읽음여부`, `읽은일시` 둘 다 있음
- **DDL**: `read_yn` 제거, `read_at IS NULL`로 판단
- 👉 ERD에서 `읽음여부` 삭제(파생 속성) 필요.

### 1-9. 신고 사유 코드

| 기술서 TRS-01 ③④ | DDL `reason_code` |
| --- | --- |
| 허위 상품 정보 | ❌ 없음 |
| 금지 물품 판매 | ❌ 없음 |
| 부적절한 게시글 | 부적절한게시물 |
| 사기 의심 | 사기의심 |
| 욕설 및 비방 | 욕설/비방 |
| 부적절한 거래 행위 | ❌ 없음 |
| ❌ 없음 | 스팸/광고 |
| ❌ 없음 | 기타 |

👉 한쪽으로 맞춰야 함. (데모 구현은 DDL 값 사용)

### 1-10. 신고 내용 필수 여부
- **기술서 TRS-01 ⑤**: 구체적인 신고 내용을 "작성해야 한다" (필수)
- **DDL**: `report.content NULL` (선택)

### 1-11. 신고 증빙자료
- **ADM-03 ⑤⑧**: 증빙자료 검토, 증빙 불충분 시 반려
- **ERD / DDL / 엔티티 내역**: 증빙자료(첨부) 속성 없음
- 👉 "증빙 = 신고 내용 텍스트"로 문구 정리하거나 첨부 테이블 추가.

### 1-12. 탈퇴 시 개인정보 처리 vs 동일 row 재사용
- **기술서 MEM-01 ⑧**: 탈퇴 시 개인정보 삭제 또는 분리 보관 / ⑨ 재가입은 최초 가입과 동일 절차
- **회의록2-2 / DDL(P-01, P-02)**: 같은 row를 '정상'으로 되돌려 재사용, 게시글·판매기록 보존
- 충돌: 개인정보를 지우면 재가입자를 같은 row에 매칭할 방법이 없고, 지우지 않으면 닉네임·이메일·전화번호 UNIQUE 때문에 탈퇴자의 값으로는 신규 가입 불가
- 👉 "재가입 = 이메일(또는 전화번호)로 기존 row 찾아 재활성화"로 규칙 확정 필요. (데모 구현은 이 방식)

### 1-13. 탈퇴 제한 조건
- **기술서 MEM-01 ⑦**: "판매 중인 상품"이 있으면 완료 또는 삭제해야 함
- **흐름도 2쪽**: "진행 중인 거래/상품 확인", "판매중 상품 존재 (탈퇴 제한)"
- '예약중' 상품도 막는지 불명확, DDL에는 강제 없음 (앱에서 처리)
- 👉 "판매중·예약중 상품이 하나라도 있으면 탈퇴 불가"로 명시 권장.

### 1-14. 로그인 실패 사유 "피신고 계정"
- **흐름도 2쪽**: 로그인 실패 화살표 라벨 "불일치/**피신고 계정**"
- **기술서 MEM-02 ④**: 계정상태가 '정상'이 아니면(탈퇴·이용정지) 로그인 불가. 신고당했다는 것만으로 막지 않음
- 👉 흐름도 라벨을 "불일치/이용정지·탈퇴 계정"으로 수정.

### 1-15. 권한(role) 관련 업무가 기술서·흐름도에 없음
- **회의록2-3, 2-4**: 4단계 권한, 루트는 1개·삭제 불가·권한 변경 불가, 루트가 다른 회원 권한 관리
- **DDL**: 위 규칙을 트리거·생성 컬럼으로 구현 (P-05~P-08)
- **기술서 / 흐름도**: "관리자"만 등장. moderator·staff·root 구분, 권한 부여·회수 업무(예: ADM-04) 없음
- **DDL 주석**: "모더레이터와 어드민의 기능 구분은 팀 미결정"
- 👉 권한 관리 단위업무 추가 + moderator/staff 기능 범위 결정 필요.

## 2. 🟡 명칭·값이 다른 부분

| 항목 | 기술서 본문 | 기술서 엔티티 내역 | ERD | DDL |
| --- | --- | --- | --- | --- |
| 상품 엔티티명 | 상품 / 상품 게시글 | 상품 | **상품 게시글** | product (상품) |
| 게시글 조치 엔티티명 | — | 게시글 관리 이력 | **게시글 조치** | product_action (상품 게시글 관리 이력) |
| 신고 처리 엔티티명 | — | 신고 처리 | 신고 처리 | report_process (**신고 처리 이력**) |
| 상품의 상태 | 상품 상태 | 상품상태 | **물품상태** | item_condition (물품상태) |
| 상품 상태 값 | 정의 없음 | 정의 없음 | 정의 없음 | 새상품 / 거의새것 / 사용감있음 / 하자있음 |
| 신고 처리 결과 값 | '조치 완료', '조치 없음', '반려' | — | — | 조치완료 / 조치없음 / 반려 (띄어쓰기) |
| 생년월일·집주소 | MEM-01 ② 가입 시 "등록" (필수로 읽힘) | — | — | `NULL` 허용 (선택) |

👉 "상품" vs "상품 게시글", "상품 상태" vs "물품상태"는 거래상태·게시글상태와 혼동되므로 **물품상태**로 통일 권장.

## 3. 🟡 단위업무 번호 불일치

| 위치 | 적힌 번호 | 실제 (기술서 본문 기준) |
| --- | --- | --- |
| 기술서 PRD-03 ③④ | TRD-04 예약자 지정 | **TRD-03** 예약자 지정 |
| 기술서 PRD-03 ⑤ | TRD-05 거래 완료 처리 | **TRD-04** 거래 완료 처리 |
| DDL 헤더·report 주석 | TRS-03 | 기술서에는 **TRS-01** 신고만 있음 |
| DDL product 주석 | PRD-04 | 기술서에는 PRD-01~03만 있음 |

흐름도는 TRD-03 예약자 지정 / TRD-04 거래 완료로 기술서 본문과 일치. DDL의 TRS-03, PRD-04는 업무 기능도 번호일 수 있어 업무 기능도와 대조 필요.

## 4. ⚪ 오타·표기

- 기술서 1쪽 시스템명: `중고거래 플랫폼 "이름"` — 플랫폼 이름 미정 placeholder. 다른 쪽은 `중고거래 플랫폼`
- 기술서 TRD-04: ⑧ 다음 번호가 **⑮**, 그다음 ⑨ → 번호 순서 깨짐
- 기술서 MEM-01 ⑦: "거래**을**" → "거래를"
- 기술서 TRS-01 ⑤: 문장 끝 "한다**,**" → "한다."
- 흐름도 2쪽 중복 확인 박스: "(이메일/전화번호 등)" → 닉네임도 중복 확인 대상 (MEM-01 ③)
- 회의록1 일정: "11/15~11/20 개발" vs 회의록2 "11/15 전체 피드백·완성" — 충돌은 아니지만 개발 시작일 재확인

## 5. 데모 구현에서 임시로 택한 해석
문서가 확정되기 전까지 코드는 아래 기준으로 만든다. 확정되면 해당 부분만 바꾸면 됨.

1. 로그인 = 닉네임 + 패스워드, 5회 연속 실패 시 10분 잠금
2. 관리자 = `member.role IN (moderator, staff, root)`, 기능 구분 없음. 권한 변경은 root만
3. 재가입 = 같은 이메일의 탈퇴 row를 재활성화
4. 탈퇴 불가 조건 = 판매중·예약중 상품 보유
5. 거래 완료 = 판매중/예약중 모두 가능, 구매자는 해당 상품 채팅 참여자 중 선택
6. 채팅방 = 상품·구매자당 1개 (DDL 기준), 판매완료 시 최종 구매자 외 방은 비활성
7. 신고 사유 = DDL enum 값
