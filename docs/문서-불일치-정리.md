## 0-1. 🔴 단위업무 번호 체계가 두 갈래

같은 업무를 문서마다 다른 번호로 부른다.

| 업무 | 기능도 | DDL 주석 | 기술서 본문 참조 (PRD-03) | 기술서 제목 | 흐름도 |
| --- | --- | --- | --- | --- | --- |
| 거래 상태 변경 | **PRD-04** | PRD-04 | — | PRD-03 | PRD-03 |
| 예약자 지정 | **TRD-04** | — | TRD-04 | TRD-03 | TRD-03 |
| 거래 완료 처리 | **TRD-05** | — | TRD-05 | TRD-04 | TRD-04 |
| 신고 | **TRS-03** | TRS-03 | — | TRS-01 | TRS-01 |
| 신고 처리 | ADM-03 **신고 처리** | ADM-03 | — | ADM-03 **신고 관리** | ADM-03 |

- 기능도에는 PRD-03, TRD-03, TRS-01·02가 비어 있다. 중간 업무를 빼면서 번호를 다시 매기지 않은 것으로 보인다.
- 기술서 PRD-03 본문은 기능도 번호(TRD-04, TRD-05)를 쓰는데, 기술서 제목은 다른 번호를 써서 **기술서 안에서도 충돌**한다.
- 👉 기능도를 기준으로 하고, 기술서 제목과 흐름도의 번호를 고치는 쪽이 수정량이 가장 적다(DDL도 이미 기능도 번호를 쓴다). 반대로 빈 번호를 없애려면 기능도·DDL·기술서 본문을 모두 고쳐야 한다.
- 코드 주석과 README는 **기능도 번호**로 맞췄다. 주석의 ①② 같은 문단 번호는 기술서 문단을 가리킨다.

## 1. 🔴 구조·규칙이 갈리는 부분

### 1-1. 관리자 엔티티 존재 여부
- **기술서 엔티티 내역 #6**: 별도 `관리자` 엔티티 (관리자번호, 관리자아이디, 패스워드해시, 관리자권한, 계정상태)
- **회의록2 / 개념·논리·물리ERD / DDL**: 관리자 테이블 없음. `회원.role`(user / moderator / staff / root)로 관리하고, 관리자번호 = 회원번호
- 👉 기술서 엔티티 내역에서 `관리자`를 빼고 `회원`에 `권한(role)`을 추가해야 한다. ADM-01 ⑦, ADM-02 ⑩, ADM-03 ⑪의 "관리자번호"는 ERD처럼 "관리자 회원번호"로 통일하는 것을 권장한다.

### 1-2. 기술서 엔티티 내역에 빠진 엔티티·속성
기술서 본문과 ERD 3종·DDL에는 있는데 엔티티 내역(12쪽)에만 없는 것들이다.

| 엔티티 | 빠진 것 | 근거 |
| --- | --- | --- |
| 채팅 메시지 | **엔티티 자체가 없음** | 기술서 TRD-02 전체 |
| 회원 | 권한, 연속로그인실패횟수, 로그인제한만료일시 | 회의록2-3, MEM-02 ⑦ |
| 상품 | 구매자회원번호(FK), 거래완료일시 | TRD-04 ⑥ |

### 1-3. 로그인 수단 / "아이디"
- **기술서 MEM-02 ①②**: 닉네임 + 패스워드로 로그인
- **기능도 MEM-01**: "**아이디**/닉네임 중복 확인"
- **기술서 ADM-01 ②**: "회원번호, **아이디**, 닉네임…"으로 검색
- **기술서 엔티티 #6**: 관리자아이디
- **ERD 3종 / DDL**: 아이디 컬럼 없음 (닉네임·이메일·전화번호가 UNIQUE)
- 👉 "아이디 = 닉네임"으로 확정하고 기능도·ADM-01 ② 문구를 고치거나, 아이디 컬럼을 추가해야 한다. 데모는 닉네임 로그인 기준이다.

### 1-4. 거래 완료 흐름: 구매자 수령 확인 단계
- **흐름도 1쪽**: 판매자 "물품 전달" → 구매자 "물품 수령 확인" → "수령 완료" → 판매자 거래 완료
- **기술서 TRD-04 / 기능도 TRD-05**: 판매자가 혼자 완료 처리하고, 구매자 확인 단계는 없다
- **DDL**: 수령 확인 관련 컬럼 없음
- 👉 흐름도의 수령 확인 단계를 "오프라인 단계(시스템 기록 없음)"로 표시하거나 삭제해야 한다.

### 1-5. 거래 완료가 '예약중'을 거쳐야 하는가
- **흐름도 1쪽**: 판매완료는 예약중 → 최종 확정 경로로만 그려져 있다
- **기술서 TRD-04 ④**: 예약중이면 예약자를 구매자로 고를 수 있다고만 되어 있고, 판매중에서 바로 완료할 수 있는지는 불명확하다
- **DDL**: 판매중 → 판매완료 직행을 허용한다 (구매자 ≠ 예약자도 허용)
- 👉 규칙을 하나로 확정해야 한다. 데모는 판매중·예약중 모두에서 완료 가능하고, 구매자는 해당 상품 채팅방 참여자로 제한한다.

### 1-6. 채팅방 중복 개설 규칙
- **기술서 TRD-01 ④**: "이미 **활성화된** 채팅방이 있으면 기존 방으로 연결" → 비활성 방이면 새로 만들 수 있다는 뜻으로 읽힌다
- **기능도 TRD-01**: "중복 개설 방지"
- **DDL**: `UNIQUE (product_no, buyer_no)` → 상태와 무관하게 상품·구매자당 1개
- 👉 기술서 문구를 "이미 채팅방이 존재하는 경우"로 바꾸면 기능도·DDL과 맞는다.

### 1-7. 거래 완료 후 채팅방 1개월 유지
- **기술서 TRD-04 ⑩**: 최종 구매자 방은 완료 후 1개월간 활성 상태를 유지한다 (이후 비활성 전환을 암시)
- **DDL / 흐름도**: 1개월 후 전환 규칙이나 배치 작업이 없다 (`product.completed_at`으로 계산은 가능)
- 👉 "완료일시 + 1개월이 지나면 전송 불가"를 조회 시 계산으로 처리한다고 명시하는 것을 권장한다. 데모는 이 방식이다.

### 1-8. 메시지 읽음 여부 컬럼
- **기술서 TRD-02 ⑥**: 읽음 여부 + 읽은 일시
- **개념ERD**: `읽음여부`, `읽은일시` 둘 다 있음
- **논리ERD / 물리ERD**: `read_yn boolean (0:안읽음, 1:읽음)` + `read_at`
- **DDL**: `read_yn`을 제거하고 `read_at IS NULL`로 판단 (DDL 주석에 명시)
- 👉 DDL 쪽 결정이 맞다(읽음여부는 읽은일시에서 파생된다). 논리·물리ERD에서 `read_yn`을 삭제하고, 개념ERD에서 `읽음여부`를 삭제해야 한다.

### 1-10. 신고 내용 필수 여부
- **기술서 TRS-01 ⑤**: 구체적인 신고 내용을 "작성해야 한다" (필수)
- **DDL**: `report.content NULL` (선택)
- 데모는 화면과 API에서 필수로 받는다.

### 1-11. 신고 증빙자료
- **기술서 ADM-03 ⑤⑧**: 증빙자료를 검토하고, 증빙이 불충분하면 반려
- **ERD 3종 / DDL / 엔티티 내역**: 증빙자료(첨부) 속성이 없다
- 👉 "증빙 = 신고 내용 텍스트"로 문구를 정리하거나, 첨부 테이블을 추가해야 한다.

### 1-12. 탈퇴 시 개인정보 처리 vs 같은 row 재사용
- **기술서 MEM-01 ⑧**: 탈퇴 시 개인정보를 삭제하거나 분리 보관 / ⑨ 재가입은 최초 가입과 같은 절차
- **회의록2-2 / DDL(P-01, P-02)**: 같은 row를 '정상'으로 되돌려 재사용하고, 게시글·판매기록은 보존
- 충돌: 개인정보를 지우면 재가입자를 같은 row에 연결할 방법이 없다. 지우지 않으면 닉네임·이메일·전화번호 UNIQUE 때문에 탈퇴자의 값으로 신규 가입을 할 수 없다.
- 👉 "재가입 = 이메일로 기존 row를 찾아 재활성화"로 규칙을 확정해야 한다. 데모는 이 방식이다.

### 1-13. 탈퇴 제한 조건
- **기술서 MEM-01 ⑦**: "판매 중인 상품"이 있으면 거래를 완료하거나 삭제해야 한다
- **흐름도 2쪽**: "진행 중인 거래/상품 확인", "판매중 상품 존재 (탈퇴 제한)"
- **기능도**: 회원탈퇴 기능 자체가 없다 (MEM-01은 가입만, 아래 2-1 참고)
- '예약중' 상품도 막는지 불명확하고, DDL에는 강제 장치가 없다 (앱에서 처리)
- 👉 "판매중·예약중 상품이 하나라도 있으면 탈퇴 불가"로 명시하는 것을 권장한다. 데모는 이 방식이다.

### 1-14. 로그인 실패 사유 "피신고 계정"
- **흐름도 2쪽**: 로그인 실패 화살표 라벨 "불일치/**피신고 계정**"
- **기술서 MEM-02 ④**: 계정상태가 '정상'이 아니면(탈퇴·이용정지) 로그인 불가. 신고당했다는 것만으로는 막지 않는다
- 👉 흐름도 라벨을 "불일치/이용정지·탈퇴 계정"으로 고쳐야 한다.

### 1-15. 권한(role) 관련 업무가 기능도·기술서·흐름도에 없음
- **회의록2-3, 2-4**: 4단계 권한, 루트는 1개·삭제 불가·권한 변경 불가, 루트가 다른 회원의 권한을 관리
- **ERD 3종**: `권한역할(0:user, 1:moderator, 2:staff, 3:root)`
- **DDL**: 위 규칙을 트리거·생성 컬럼으로 구현 (P-05~P-08)
- **기능도 / 기술서 / 흐름도**: "관리자"만 등장한다. moderator·staff·root 구분이 없고, 권한 부여·회수 업무(예: ADM-04)도 없다
- **DDL 주석**: "모더레이터와 어드민의 기능 구분은 팀 미결정"
- 👉 기능도에 권한 관리 단위업무를 추가하고, moderator/staff 기능 범위를 결정해야 한다.

### 1-16. 신고 1건당 처리 이력 개수
- **개념ERD**: 신고 1 — 처리 결과 — 1 신고 처리 (1:1)
- **물리ERD**: REPORT ‖—○+ REPORT_PROCESS (1:0..1)
- **DDL**: `report_process.report_no`에 UNIQUE가 없고, 주석에 "신고 1건 : 처리 이력 N건"이라고 되어 있다 (1:N)
- 👉 1:1로 갈 거면 DDL에 `UNIQUE (report_no)`를 추가하고 이름을 "신고 처리"로 바꾼다. 1:N(재처리 이력 보존)으로 갈 거면 ERD를 고친다. 데모는 처리완료·반려된 신고를 다시 처리하지 못하게 막아서, 실제 동작은 1:0..1이다.

## 5. ⚪ 오타·표기

- 기술서 1쪽 시스템명: `중고거래 플랫폼 "이름"`. 플랫폼 이름이 미정인 placeholder다. 다른 쪽과 기능도는 `중고거래 플랫폼`
- 기술서 TRD-04: ⑧ 다음 번호가 **⑮**, 그다음이 ⑨ → 번호 순서가 깨져 있다
- 기술서 MEM-01 ⑦: "거래**을**" → "거래를"
- 기술서 TRS-01 ⑤: 문장 끝 "한다**,**" → "한다."
- 흐름도 2쪽 중복 확인 박스: "(이메일/전화번호 등)" → 닉네임도 중복 확인 대상이다 (MEM-01 ③)
- 개요서 3.2 Q2, 3.3 Q1: 질문이 비어 있다. 2쪽은 빈 페이지다
- 회의록1 일정: "11/15~11/20 개발" vs 회의록2 "11/15 전체 피드백·완성". 충돌은 아니지만 개발 시작일을 다시 확인하는 것이 좋다

## 7. 데모 구현에서 임시로 택한 해석
문서가 확정되기 전까지 코드는 아래 기준으로 동작한다. 확정되면 해당 부분만 바꾸면 된다.

1. 단위업무 번호 = 기능도 기준 (PRD-04, TRD-04 예약, TRD-05 완료, TRS-03 신고)
2. 로그인 = 닉네임 + 패스워드, 5회 연속 실패 시 10분 잠금
3. 중복 확인 = 닉네임·이메일·전화번호 (가입 화면의 "중복 확인" 버튼, `GET /auth/check`)
4. 관리자 = `member.role IN (moderator, staff, root)`, 기능 구분 없음. 권한 변경은 root만
5. 재가입 = 같은 이메일의 탈퇴 row를 재활성화
6. 탈퇴 불가 조건 = 판매중·예약중 상품 보유
7. 거래 완료 = 판매중·예약중 모두 가능, 구매자는 해당 상품 채팅 참여자 중에서 선택
8. 채팅방 = 상품·구매자당 1개 (DDL 기준). 판매완료 시 최종 구매자 외의 방은 비활성. 최종 구매자 방은 완료 후 30일까지 전송 가능
9. 판매자가 '정상'이 아니면(탈퇴·이용정지) 새 채팅방을 열 수 없음
10. 신고 사유 = DDL enum 값, 신고 내용은 필수
11. 신고 처리 = 처리완료·반려 후에는 재처리 불가 (실질 1:0..1)
12. 읽음 여부 = `read_at IS NULL` (DDL 기준)
